# Two M5.2 misses with manually verified prior work

Both sources were available before the M5.2 inputs were selected. This retrospective reads the upstream files at release commits and compares them with the original decisions. Manual finds leave the original automated scores at zero. No receiving-project or GPU test was run in this review. [Frozen questions](../m52/intent.md) · [M5.2 rankings](../m52/assessment.md) · [Actual queries](../m52/search-responses.json)

## XCL #2852 — when to erase a command list's tracking

**Already in the origin.** The PR links XCL #2690, which describes an old command list's cleanup erasing a new list's state when the native address is reused. The frozen patch uses the native `AddRef` return value to decide when to forget the entries. The idea of erasing them earlier was already public in XCL. [Origin](https://github.com/xcl-dev/xcl/pull/2852) · [Linked issue](https://github.com/xcl-dev/xcl/issues/2690) · [Frozen release wrapper](https://github.com/xcl-dev/xcl/blob/69ebece8a98ae956556eb02d3721db712501e9b2/crates/xcl/src/hle/d3d12x/real.rs#L7137-L7153)

**Independent implementation.** RenderDoc v1.37 registers a wrapper under the real `ID3D12GraphicsCommandList` pointer. When its own wrapper count reaches zero, it destroys the wrapper. The destructor removes that pointer's entry from the map while the native list is still held, then releases the native list interfaces. The resource-manager code confirms that removal actually erases the key. Microsoft documents the native `AddRef` return count as a diagnostic value. [Registration](https://github.com/baldurk/renderdoc/blob/cd94206b0fd995bfb3e5ed95c1e68d4f5d38ea7e/renderdoc/driver/d3d12/d3d12_commands.cpp#L1402-L1410) · [Wrapper count](https://github.com/baldurk/renderdoc/blob/cd94206b0fd995bfb3e5ed95c1e68d4f5d38ea7e/renderdoc/driver/d3d12/d3d12_command_list.h#L287-L295) · [Destructor order](https://github.com/baldurk/renderdoc/blob/cd94206b0fd995bfb3e5ed95c1e68d4f5d38ea7e/renderdoc/driver/d3d12/d3d12_commands.cpp#L1414-L1450) · [Map erase](https://github.com/baldurk/renderdoc/blob/cd94206b0fd995bfb3e5ed95c1e68d4f5d38ea7e/renderdoc/core/resource_manager.h#L1804-L1817) · [Microsoft COM contract](https://learn.microsoft.com/en-us/windows/win32/api/unknwn/nf-unknwn-iunknown-addref#return-value)

**Decision.** Review whether XCL can control finalization and hold the native object until its pointer-keyed tracking is gone. RenderDoc supplies a concrete ownership and ordering precedent for the same interface. XCL still needs to establish that its own hooks observe all relevant references and preserve state across ordinary nonfinal releases.

**Where Discovery lost it.** XCL supplies an explicit issue relation. M5.2 issued a single issues search for `command list`, dropping final release and address reuse. It neither followed #2690 nor searched file contents. RenderDoc was outside the queried repositories.

## Continued #2392 — which precompiled entry the runtime can reuse

**Already in the origin.** The PR identifies differences between the standalone checker and the playing runtime. The frozen runtime hashes compute shader bytes, entry point, pipeline and shader-stage flags, subgroup size and layout inputs into the journal name. It also checks device identity before skipping an existing journal file. Using the runtime builder is the author's solution. [Origin](https://github.com/ubiquitarianism/leonida/pull/2392) · [Runtime key and file check](https://github.com/ubiquitarianism/leonida/blob/8a73cb09be44c908d7fbe4947d2510ee8c95e7c1/runtime/shims/d3d12_vulkan_device.cpp#L10938-L10970)

**Independent implementation and measurement.** Godot 4.4 checks persisted cache data against vendor, device, driver version, cache UUID and ABI before passing accepted bytes to Vulkan. Its compute builder supplies the actual shader stage, layout and specialization data with the cache. Driver version and ABI checks are Godot policy. Vulkan's version-one header contains vendor ID, device ID and cache UUID. [Godot load path](https://github.com/godotengine/godot/blob/4c311cbee68c0b66ff8ebb8b0defdd9979dd2a41/drivers/vulkan/rendering_device_driver_vulkan.cpp#L4494-L4524) · [Godot compute builder](https://github.com/godotengine/godot/blob/4c311cbee68c0b66ff8ebb8b0defdd9979dd2a41/drivers/vulkan/rendering_device_driver_vulkan.cpp#L5296-L5325) · [Vulkan 1.3.290 header](https://github.com/KhronosGroup/Vulkan-Docs/blob/043260d06e96c8586492be41cc109945e92a69ff/chapters/pipelines.adoc#L7515-L7525)

**Decision.** For a synthetic compute shader, compare the offline and playing paths' journal key and device identity. Then ask the playing path to create that pipeline from those saved bytes in a fresh process. Where creation feedback is supported, a valid pipeline-level application-cache-hit bit confirms reuse of the supplied cache. Khronos's compute conformance test recreates a pipeline and checks that feedback. It treats a missing hit on a warmed cache as a quality warning. A shared filename or successful pipeline creation alone leaves the driver hit unverified. This check covers compute. Graphics requires its own draw-time state. [Vulkan feedback definition](https://github.com/KhronosGroup/Vulkan-Docs/blob/043260d06e96c8586492be41cc109945e92a69ff/chapters/VK_EXT_pipeline_creation_feedback/pipelines.adoc#L112-L139) · [Khronos compute test](https://github.com/KhronosGroup/VK-GL-CTS/blob/65fff6ac4d782ad42a490b007376e84159a113e3/external/vulkancts/modules/vulkan/pipeline/vktPipelineCreationFeedbackTests.cpp#L1029-L1058) · [Warm-case grading](https://github.com/KhronosGroup/VK-GL-CTS/blob/65fff6ac4d782ad42a490b007376e84159a113e3/external/vulkancts/modules/vulkan/pipeline/vktPipelineCreationFeedbackTests.cpp#L1147-L1153)

**Where Discovery lost it.** M5.2 selected `vk_shader_stage_all`, one incidental difference already named by the author. The search omitted both cache compatibility and precompile/runtime reuse. Vulkan-Docs was in scope, but only its issues and PRs were queried. The normative chapter and conformance-test code could never appear as file results in that request.
